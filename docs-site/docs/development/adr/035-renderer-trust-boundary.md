# ADR 035: Renderer Trust Boundary with Context Isolation Disabled

## Status

✅ Implemented (v2.24.0 and v2.30.0)

The sender-pinning, emitter and webview fixes shipped in v2.24.0 ([PR #3053](https://github.com/IsmaelMartinez/teams-for-linux/pull/3053), [PR #3054](https://github.com/IsmaelMartinez/teams-for-linux/pull/3054), [PR #3055](https://github.com/IsmaelMartinez/teams-for-linux/pull/3055)). The preload hardening, credential-free config and session permission handlers shipped in v2.30.0 ([PR #3184](https://github.com/IsmaelMartinez/teams-for-linux/pull/3184), [PR #3185](https://github.com/IsmaelMartinez/teams-for-linux/pull/3185)). Rule 8, on unsandboxed popups, was added in November 2026 after the move to Electron 45. Rules 9 and 10 close the item the reports left open, a navigation lock in front of the preload: the main process now checks the sender of every channel, and a navigation guard watches the Teams window and the profile views. The guard only observes by default, so the preload can still run on a foreign page until the user turns the lock on (see Consequences).

## Context

The Teams window runs with `contextIsolation: false` and `sandbox: false` because `reactHandler` reads Teams' React internals for presence, idle sync and custom backgrounds; `nodeIntegration` stays `false`. The [security architecture](../security-architecture.md) has recorded that trade-off since 2025, together with the compensating controls: CSP headers, the IPC channel allowlist and payload sanitiser, domain checks on DOM access.

Three private reports in October and November 2026 showed that the allowlist alone did not bound what page script could do, because with context isolation off the page and the preload share one JavaScript world:

- [GHSA-3vg9-cwq9-p773](https://github.com/IsmaelMartinez/teams-for-linux/security/advisories/GHSA-3vg9-cwq9-p773): the preload's listener helpers returned the result of `ipcRenderer.on`, which is the raw `ipcRenderer`, and passed Electron's IPC event (whose `sender` is the same object) to page callbacks. The picker channels then answered any sender, so web content could capture the desktop without consent.
- [GHSA-6xpg-fhf9-chcr](https://github.com/IsmaelMartinez/teams-for-linux/security/advisories/GHSA-6xpg-fhf9-chcr): the sticker importer wrote attacker-controlled bytes to disk and disclosed the path, and an unvetted `<webview>` could load that file as an unsandboxed preload, which runs with Node.js.
- [GHSA-58j7-22f8-6xqp](https://github.com/IsmaelMartinez/teams-for-linux/security/advisories/GHSA-58j7-22f8-6xqp): even after the first fix, page script could patch the shared built-ins (`Object.prototype`, `Function.prototype`, `WeakMap.prototype`, the array iterator), dispatch a synthetic `DOMContentLoaded` and have the preload re-initialise through code it controlled, recovering `ipcRenderer` from the objects that stored it. The generic `electronAPI.send` then reached every allowlisted channel, `get-config` returned the full configuration including MQTT and certificate passwords, no session had a permission handler so any popup or in-app page got microphone and camera without a prompt, and nothing stopped a navigation away from Teams while the privileged preload stayed attached.

The precondition in every case is script running in the Teams window, through an XSS in Teams web or a page loaded there. The reports made explicit what the earlier controls assumed away: a channel allowlist is not a boundary when the caller is inside the same world as the code that calls it.

## Decision

Treat the whole JavaScript world of the Teams window and of every profile view as page-controlled, and move trust to places page script cannot reach: preload closures, the sender frame as seen by the main process, and the session.

1. **Nothing Electron-native leaves the preload.** Listener helpers return nothing and strip the IPC event before calling back. The generic `electronAPI.send` is gone; the page sees only named `electronAPI` methods, each bound to a fixed channel with shaped arguments.
2. **`ipcRenderer` lives only in closures and private fields.** Browser tools flagged `ipc: true` still receive the full `ipcRenderer` through `init(config, ipcRenderer)`; the restriction is on where they keep it, in `#private` fields under strict mode, not on what they receive. The narrowing applies to the page-facing `electronAPI`, not to the tools. Strict mode is a security requirement, not style: `EventEmitter` calls listeners with `this` set to the raw `ipcRenderer`, and V8's `CallSite.getThis` hands that receiver to any sloppy-mode frame; `tests/unit/preloadIpcLeak.test.js` fails for any file that registers a listener without it.
3. **Initialisation runs once, on the browser's own event.** The `DOMContentLoaded` handler returns unless `event.isTrusted` and a module-level started flag is clear. The module list is walked with an indexed loop over own properties, not `for...of` or `Set.has`, and every entry sets its own `ipc` flag, because page script runs first and can patch the shared array and set built-ins or `Object.prototype`. The modules that need `ipcRenderer` (`trayIconRenderer` and `mqttStatusMonitor` among them, see AGENTS.md and [#1902](https://github.com/IsmaelMartinez/teams-for-linux/issues/1902)) still receive it at init, through that guarded path.
4. **The main process trusts the sender frame, not the channel name.** `ipcValidator` keeps the allowlist and payload sanitiser, and adds sender pinning (`appPageOnlyChannels`): the screen-share picker channels, the profile channels and all seven Graph channels answer only `file:` senders inside the app directory. The Teams page has no `electronAPI.graphApi`: nothing in the app called its five methods, so they were removed and their channels pinned too. Profile URLs must be `https`. The wrapper in `ipcSecurity` makes a pending `once()` listener removable so a rejected sender cannot consume the picker's handler.
5. **The renderer gets a credential-free config.** `get-config` returns `toRendererConfig(config)` (`app/config/rendererConfig.js`), a copy without MQTT, basic-auth or client-certificate secrets, because anything that handler returns is readable by page script.
6. **Webview attach is refused everywhere.** `webviewTag: false` in the root window and every profile view, plus an app-wide `will-attach-webview` refusal for any webContents created later. The sticker importer additionally checks the declared image signature before saving.
7. **Device permissions follow the requester, on every session.** `app/security/permissions.js` installs request and check handlers on the default session and each profile partition. Teams, government Teams, the Microsoft sign-in hosts, the configured URL, `https` profile URLs and the app's own `file:` pages get full access. A cross-origin frame inside a trusted page keeps only what Chromium already gates per frame with Permissions Policy (media, display capture, clipboard, fullscreen). Any other page may only open `mailto:` and `tel:` links. Denials are logged once per permission and origin, without the URL path.
8. **A popup runs unsandboxed only as a locked blank document.** Since Electron 45 a `window.open` child whose sandbox setting differs from its opener's gets its own process and the opener's `window.open()` returns `null`, so a popup the Teams page renders into must carry the opener's `sandbox: false`. That setting belongs to the window, not to the document: navigated to a URL, the popup becomes an unsandboxed renderer for that site with a live `window.opener` back to Teams. The override is allowed only when all of these hold. The opener needs the returned handle to render into the child. The URL is exactly `about:blank` and the child is locked there, with `will-navigate` prevented and its own window-open handler denying everything, applied from `did-create-window` so that no later policy replaces it (the profile view manager rebinds the open handler on every descendant). The request is recognised by a per-launch frame name generated in the main process, behind a config option. The override pins `contextIsolation: true` and `nodeIntegration: false`, sets no preload, and a unit test asserts it. A popup that loads or will load a URL never gets the override: Electron 45 already isolates it, and the opener does not need its handle. The Document Picture-in-Picture popup prompted this rule: [PR #3232](https://github.com/IsmaelMartinez/teams-for-linux/pull/3232) adds the `sandbox: false` override and has to add the lock and the pinned preferences before it merges. A later popup reuses those helpers rather than copying the literal.
9. **Every channel checks the sender frame, not only the pinned ones.** The preload runs on every top-level page the window shows, including federated identity provider pages whose hosts cannot be known in advance, so rule 4's pinned list is no longer the only gate. `isSenderAllowed` puts each allowlisted channel in one of three classes, reading `event.senderFrame.url` (never `event.sender.getURL()`, which can already name the next page). Local pages only: the pinned channels plus every channel whose only sender is one of the app's own dialogs, prompts and toasts. Any sender: a short list pinned by a test, each entry justified in code (`get-config`, which the preload cannot initialise without and which is credential-free; `get-zoom-level`; `title-bar-overlay-update`, whose handler accepts only a bounded height and two hex colours; and `webauthn:create` and `webauthn:get`, which enforce their own origin allowlist that includes configured identity provider origins). Everything else: the app's local pages and trusted web pages, the predicate rule 7 uses (Teams, the sign-in hosts, the configured URL and the `https` profile URLs). A call with no event at all is an in-process `ipcMain.emit` and stays allowed, since a renderer message always carries an event. Refusals are logged once per channel with the sender's scheme only.
10. **A navigation guard watches the Teams window and every profile view.** `app/security/navigationGuard.js` listens to `will-navigate` and `will-redirect` on main frames. A destination is trusted when it passes the rule 9 predicate, is listed in `urlHandling.navigationLock.extraOrigins` or `auth.webauthn.extraOrigins`, is accepted by `auth.webLogin.extraHosts`, is `about:blank`, or is a `blob:` URL whose inner origin is trusted. A link the operating system opens (`mailto:`, `tel:`, `msteams:` and the like) fires `will-navigate` too, but it never puts a page in the window, so the guard ignores it and rule 7's `openExternal` decision still applies. By default the guard only observes: the first navigation to each other origin in a session is logged once, with its scheme and whether it was a navigation or a redirect, and a hint names the option. With `urlHandling.navigationLock.enabled` it cancels the navigation, logs a warning without the origin and shows a non-blocking dialog that names the origin and says how to allow it. A cancelled redirect rejects the `loadURL()` that started it, so every `loadURL` on these webContents handles its rejection.

The rules above are the contract for every new browser tool: no return of Electron objects to the page, `ipcRenderer` in a private field, strict mode, a sender check on any new privileged channel, and no unsandboxed popup outside rule 8.

## Consequences

### Positive

Script in the Teams window is bounded to the allowlisted channels with the argument shaping the preload applies, and the pinned channels (picker, profiles, people search, chat send) answer only the app's own pages. It cannot capture the screen, read credentials, add a profile that loads another origin with the preload, or obtain device permissions for a page outside the trusted set. Every other channel answers only the app's pages and trusted web pages, so a federated sign-in page the window has been sent to can no longer raise notifications, change the tray, publish to MQTT or trigger the incoming-call command. A trusted-origin popup can still be granted the microphone, which is why the permission policy is requester-based rather than a blanket popup denial. Each rule is enforced by code or a unit test rather than by review memory, which matters for a surface that has regressed before ([#1902](https://github.com/IsmaelMartinez/teams-for-linux/issues/1902)).

### Negative

The shared world remains. Context isolation is still off, so these are compensating controls around a missing boundary, not the boundary itself, and a future preload change can reopen a path by storing `ipcRenderer` on a reachable object or iterating with a patchable built-in. Every browser tool carries the extra discipline, and the trusted-requester list in `permissions.js` must be extended when Teams moves to a new host. The navigation lock from GHSA-58j7 item 4 is off by default, because a federated tenant's sign-in site cannot be known in advance and blocking it would stop that user signing in. Until the user turns it on, a top-level navigation out of Teams still carries the preload with it: the page runs the preload's tools, can read the credential-free `get-config` answer, and can reach the five any-sender channels, though no other channel answers it. The `extraOrigins` list needs the user to know their identity provider's origin, which the blocked-navigation dialog shows them. With the lock on, a redirect to an unlisted site inside the app's own first load leaves the window empty, and the connection manager treats that as a failed load and retries it, until the origin is added and the app restarted. Same-document navigations fire neither event, and popups are outside the guard because they get no preload.

### Neutral

Popups opened from a profile view do not inherit the preload (Electron gives them context isolation, a sandbox and no preload), so their reach was already limited to permissions and phishing; the permission handlers close that remaining gap. The permission policy and the sender pinning are described operationally in the [security architecture](../security-architecture.md); this record holds the reasoning.

## Alternatives Considered

### Enable `contextIsolation` and expose a `contextBridge` API

Rejected again, for the reason recorded in the security architecture: `reactHandler` needs the page's React internals, and a bridge cannot hand those across an isolated world. Presence, idle sync, custom backgrounds and parts of the authentication flow depend on it.

### Enable the Electron `sandbox` for the Teams window

Rejected on compatibility, not on IPC: a sandboxed preload keeps `ipcRenderer` (the profile switcher's preload in `app/profileSwitcher/preload.js` runs with `sandbox: true`), but the Teams preload is assembled from local CommonJS modules and uses Node modules such as `node:path` (for example `app/browser/tools/dockIconRenderer.js`), which a sandboxed preload cannot `require`. It would also not by itself close the shared world. It is worth revisiting for a different reason: with the Teams window sandboxed, popups would match their opener by default and rule 8 would no longer be needed.

### Keep the allowlist as the only control

What the project had. Reaching `ipcRenderer` does not bypass the main-process allowlist: `installIpcSecurity` still validates every call and `validateIpcChannel` rejects unknown channels. What it bypasses is the preload's narrow helpers, so every allowlisted channel becomes callable with attacker-chosen arguments. The allowlist decides which channels exist, not who may call them or with what, and with one world the caller was any page script willing to patch a prototype.
